## Findings

### High

1. None.

### Medium

1. **Inconsistent timeout truth across implementation and user messaging**
   - Files:
     - `source/install.sh`
     - `source/display.sh`
     - `source/setup_display_blanking.sh`
     - `README.md`
   - Detail:
     - Runtime scripts enforce 3/6 minute setterm behavior.
     - Boot-parameter script enforces 2 minute `consoleblank` behavior.
     - User-facing install output states 5/10 minute behavior.
   - Risk:
     - Operators cannot reliably predict effective blanking policy after install.
   - Recommendation:
     - Define one canonical timeout policy and expose alternative strategy as explicit opt-in mode.

2. **Service/timer installation assumes successful status inspection in all environments**
   - File:
     - `source/install.sh`
   - Detail:
     - Script uses `set -e` and runs `systemctl status ...` commands during install.
     - In constrained/non-standard environments, status calls can return non-zero and abort install after files are already copied.
   - Risk:
     - Partial install state with unclear rollback.
   - Recommendation:
     - Treat status inspection as informational (`|| true`) and keep transactional success criteria explicit.

3. **Two configuration strategies exist without orchestration or precedence model**
   - Files:
     - `source/display.sh`
     - `source/setup_display_blanking.sh`
     - `source/check_display_blanking.sh`
     - `README.md`
   - Detail:
     - Runtime setterm and boot-time kernel parameter workflows are independent and can conflict semantically.
   - Risk:
     - Operational drift and difficult troubleshooting.
   - Recommendation:
     - Introduce a mode selector or split into two documented products/workflows.

### Low

1. **Repair script prints installed runtime script to stdout**
   - File:
     - `source/repair.sh`
   - Detail:
     - `cat` of installed script increases noise and can leak future sensitive details if script grows.
   - Recommendation:
     - Replace with checksum/path/permission confirmation.

2. **Metadata inconsistency in project docs**
   - Files:
     - `AGENTS.md`
     - `CONTRIBUTING.md`
     - `VERSION`
   - Detail:
     - Different version values are presented in docs vs version file.
   - Recommendation:
     - Standardize metadata references to `VERSION` file values.

3. **README command examples drift from repository layout**
   - File:
     - `README.md`
   - Detail:
     - Historical examples reference scripts as root-level files while scripts live in `source/`.
   - Recommendation:
     - Keep README command paths aligned with actual repository structure.

## Positive Notes

1. Scripts consistently enforce root checks for privileged operations where required.
2. `uninstall.sh` and `repair.sh` are resilient to absent systemd units via guarded stop/disable calls.
3. Diagnostic scripts provide practical operator guidance for SSH-vs-console behavior.
4. Shell syntax quality is good (all scripts passed `bash -n`).

## Open Questions

1. Should project policy prefer kernel-level `consoleblank` or runtime `setterm` as the primary supported approach?
2. Is desktop support in scope, or should docs explicitly constrain support to server/TTY-only systems?

## Suggested Follow-Up Work

1. Consolidate timeout values into one shared config source.
2. Make install flow idempotent with explicit post-install health checks.
3. Add a lightweight smoke-test script that validates effective behavior after reboot and after timer trigger.
